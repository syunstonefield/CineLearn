# 「単語を追加」の綴りミス候補 — 設計と実測（2026-10-30・作品・予習部門）

依頼: 受付経由のオーナー要望（2026-10-30）。単語リストの「単語を追加」で入力した語が字幕に見つからない時、その話の字幕の語から綴りの近い候補を例文つきで出し、「この語ですか？」と確認できるようにする。
**状態: 設計と試作（実測スクリプト・モック）まで。コード変更なし・本番未反映。オーナーが案A／案B を選んでから実装する。**

## 0. 結論

| | 案A：共有キャッシュの字幕語だけ | 案B：案A＋その話の字幕全体（推奨） |
|---|---|---|
| 候補の取り元 | vocab_cache の drama 語（AI のおすすめ語 plus は除く） | ＋ subtitle_raw_cache の語 |
| 法務 | OK | 条件付き OK（§6 の7条件） |
| 足したい語（画面のリストに無い語）の1か所ミス・上位3件 | **2〜7%** | **97〜99%** |
| 足したい語の2か所ミス・上位3件 | ほぼ 0% | 76% |
| リストにある語の綴りミス | 96%（画面の中で判定） | 96% |
| 例文を付ける「最も近い1候補」が正解の語 | — | 96% |
| 工数 | 約1.25日 | 約2.5日（案A 込み） |

- 案A が効かないのは、足したい語のほとんど（TOEIC 700 で 99%）が、共有キャッシュに無い字幕の語だから。共有キャッシュの字幕語は、もともと単語リストに出ている語とほぼ同じ。
- オーナーの「綴りミスで追加できない、を無くしたい」に応えられるのは **案B**。

## 1. 今の流れ（2026-10-30 時点のコード）

- 画面 `components/VocabScreen.js` `handleAddWord` → `POST /api/example`（`mode:'manual'`）。
- サーバ `app/api/example/route.js`:
  - 層1: vocab_cache の字幕語（drama）と語形込みで一致すれば、その例文。
  - 層2: ログイン必須。`manualWordProblem`（3字未満・複数語・頻出語は不可）を通った語だけ、raw キャッシュ（無ければ取り直し枠の範囲で1回取得）から**完全一致（活用形込み）の1文**を返す。上限は `EXAMPLE_MANUAL_LIMITS`（1分 10・1日 100・利用者×話 20/日・話全体 60/日）。要求1回ごとに Upstash の INCR で1つ数える（`lib/ratelimit.js`）。
- 見つからなければ `no_match` になり、**入力どおりの綴りで例文なしのまま保存**される。
- 画面の「すでにこの話のリストにあります」は完全一致しか見ていない。

## 2. 実測（本番データを読み取りのみ・作業用フォルダで）

- 対象: raw キャッシュがある6本。Suits S1E6、Friends S1E1（リスト無し）、Breaking Bad S1E1、プラダを着た悪魔、Loki S1E1、ファルコン＆ウィンター・ソルジャー S1E1。
- 「足したい語」は、字幕にあって**その人の画面のリストに出ていない語**（`personalizeWords` で TOEIC 500／700／850 の3通りに絞った後）。4字以上で、頻出語・固有名詞（8割以上が大文字始まり）は除く。1話あたり 125〜365語で、そこから1話40語まで無作為に選んだ。
- 綴りミスは6種類を機械的に作った: 1字抜け／重ね字の過不足／隣の字の入れ替え／母音の取り違え／キーボードの隣のキー／音の綴り違い（ph→f・-tion→-sion・-ence↔-ance・ie↔ei など）。ミスの結果がたまたま字幕にある別の語になった場合は除外した。
- 判定は法務の条件どおり: 入力4字以上・編集距離は 5字以下=1／6字以上=2・頻出語と3字以下を除く・候補最大3。
- スクリプト: `reports/add-word-spell-mock/measure/`（`measure3.mjs`＝案A/B 比較、`measure_legal.mjs`＝種類別・2か所ミス。git 管理外）。

| TOEIC 設定 | 足したい語のうち共有キャッシュにある割合 | 案A 上位3件 | 案B 上位3件 |
|---|---|---|---|
| 500 | 8%（86/1053） | 7% | 98% |
| 700 | 1%（12/979） | 2% | 99% |
| 850 | 1%（9/976） | 2% | 97% |

- 案B の種類別（1か所ミス・上位3件）: 1字抜け 83%、ほかの5種類は 100%。1字抜けの取りこぼしは、4字の語から1字抜けて3字になり、入力4字以上の条件で候補を出さない分。
- 案B の2か所ミス: 上位3件に 76%。外れるのは主に短い語（`clnb`→climb、`wekc`→wreck など）で、距離の条件の外なので追わない。
- 案B で例文を付ける最も近い1候補が正解の語なのは 96%。
- リストにある語の綴りミス（172語）は、リストの語との比較だけで上位3件に 96%。
- 例: suspiciun→suspicion・suspicious／handkuffs→handcuffs／gntlemen→gentlemen／coincidance→coincidence。
- **正しく綴った実在の語で、その話に無いもの**を入れた場合も、案B では 11%で候補が出る（平均 1.3語。例: soap→soup）。「どれでもない」で抜けられる。これが、字幕の語を探り出すのに使える入口の大きさでもある（§5）。
- 参考: 法務の条件より広い判定（10字以上は距離3まで・音の綴り違いを距離1とみなす）にしても、1か所ミスで 100%、2か所で 81%。差が小さいので、条件のままで十分。
- 限界: ミスは機械的に作ったもので、実際の利用者のログではない。affect/effect のような「別の実在語との取り違え」は、入力した語が字幕にあればそのまま当たるので、この機能の対象外。

## 3. 出し方

モック: `reports/add-word-spell-mock/案A-スマホ（モック）.jpg`・`案B-スマホ（モック）.jpg`（元の HTML も同じ場所）。

### 案A
1. **画面の中で**、この話のリストの語との近さを先に見る。近ければ「リストにある injunction ですか？」→「リストの injunction を見る」でその行へ飛ぶ（追加はしない）。「ちがう」なら次へ。サーバには聞かない。
2. 今までどおり `/api/example` に1回聞く。層1（vocab_cache）で完全一致が無い時だけ、同じ要求の中で vocab_cache の drama 語から候補を作る。
3. 応答 `{ found:false, reason:'no_match', suggestions:[{ word, sentence?, tsSec?, tsLabel? }] }`。候補は最大3語、例文は最も近い1候補だけ（案B と同じ形にそろえる）。例文は vocab_cache の例文を `capSentence`（200字）に通す。
4. 画面: 「『coincidance』はこの話の字幕に見つかりませんでした。この語ですか？」→ 候補（語・📍時刻・“例文”・📺 作品 SxE（字幕：OpenSubtitles）。映画は話数なし）→「どれでもない（入力のまま例文なしで追加）」。

### 案B（案A に足す）
5. 層1で候補が無く、層2の関門（ログイン必須・1語・頻出語は不可）を通った語だけ、raw キャッシュの語から候補を作る。
6. 1番目の候補だけ例文・📍時刻・出典を付ける。2・3番目は語と「この語で追加」だけ。押すと、その語で今までどおり手動追加の照合をする（別の問い合わせ・完全一致の1文）。「別の例文」ボタンは作らない。
7. 選んだら、今の「追加直後のカード（意味・例文・発音）」へそのまま進む。選ばなかった候補の文は、端末にもクラウドにも保存しない。

どちらの案でも、候補が0件なら今までと同じ（例文なしで追加し、理由を一言添える）。要求の回数は増やさない（今の no_match の応答に候補を足すだけ）。

## 4. 近さの判定と工数

| 項目 | 中身 |
|---|---|
| 編集距離 | OSA（隣の字の入れ替えを1と数える）。許す距離は 5字以下=1・6字以上=2。入力4字未満は候補を出さない |
| 語形変化 | 同じ語の活用形は `wordStems` で1つにまとめ、字幕に実際に出た形を見せる。「原形を入れたが字幕は -ing 形」は今の一致処理（活用形込み）で既に当たる |
| 大文字小文字・記号 | 小文字にそろえ、アポストロフィを統一。固有名詞（8割以上が大文字始まり）・頻出語（`COMMON_WORDS`）・3字以下は候補にしない |
| 並べ順 | 距離 → 先頭の字が同じ → その話での出現回数 |

|---|---|---|

## 5. 上限の数え方（法務の条件4）と探り出しの対策

- **今**: 手動追加の要求1回ごとに、Upstash の INCR で上限キー（1分・1日・利用者×話・話全体）を1つ数える。
- **変更（案B）**: 候補一覧を返す時に、同じキーをもう1回数える（`checkRateLimit` を同じ指定で2回目に呼ぶ）。
  - 1回目の数え: 要求そのもの。完全一致の1文、または候補の1番目の1文に当たる。
  - 2回目の数え: 語だけの候補一覧（法務「語だけの候補一覧も1回に数える」）。
  - 2回目で上限を超えたら、候補を付けずに今までどおりの no_match を返す。
  - 2・3番目の候補を押した時は新しい要求なので、今までどおり1つ数える。
  - 上限の値は今のまま（1分 10・1日 100・利用者×話 20/日・話全体 60/日）。`lib/ratelimit.js` は変えずに、route だけを直す。
- 入力に近い語しか返さない。任意の語を入れて字幕の語の一覧を引き出すことはできない（正しく綴った実在の語で候補が出るのは 11%・平均 1.3語）。
- 返すのは語と1文だけ。前後の文や、全出現の時刻の並びは返さない。時刻も最も近い1候補の1つだけ。
- 候補は保存も共有キャッシュへの書き込みもしない。サーバのログは件数だけ（候補の語・文そのものは残さない）。
- 案A の層1の候補は、今の層1と同じ上限（IP×話 100/日・1分 60）の中で動く。

## 6. 法務の回答（2026-10-30・受付経由）

- vocab_cache の字幕語（drama）だけから候補を出す: OK。plus は入れない。例文は “ ” で囲み、📺 作品 SxE（字幕：OpenSubtitles）を付ける。映画は話数を書かない。
- raw からも出す: 条件付き OK。
  1. 層1で無かった時だけ raw に進む。
  2. 今の手動追加と同じ関門（ログイン必須・1語・頻出語は不可）を通った語だけ。入力4字以上。
  3. 距離 5字以下=1／6字以上=2。COMMON_WORDS と3字以下は除く。候補は最大3語。
  4. 例文は最も近い1候補だけ。ほかの候補は語だけで、押したら別の問い合わせで1文。「別の例文」は作らない。上限は見せた文の数で数え、今の値を使う。語だけの候補一覧も1回に数える。文は `capSentence`（200字）を通す。
  5. 出典表示は上と同じ。
  6. 選ばれなかった候補の文は、端末にもクラウドにも保存しない。サーバのログにも文そのものは残さない。
  7. raw が無い時の取り直しは `EXAMPLE_MANUAL_DL_LIMITS` の枠の中だけ。
- 規約・NOTICE の直しは不要。候補に CEFR の目安を付けるなら、単語帳の時の条件に従う（今回の設計では付けない）。
