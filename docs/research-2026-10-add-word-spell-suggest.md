# 「単語を追加」の綴りミス候補 — 設計と実測（2026-10-30・作品・予習部門）

依頼: 受付経由のオーナー要望（2026-10-30）。単語リストの「単語を追加」で入力した語が字幕に見つからない時、その話の字幕の語から綴りの近い候補を例文つきで出し、「この語ですか？」と確認できるようにする。
**状態: 設計と試作（実測スクリプト・モック）まで。法務の回答待ちのため本番には出さない。コード変更なし。**

## 0. 結論

- 候補は **その話の字幕（subtitle_raw_cache）の語から取る必要がある**。単語リスト（vocab_cache）の語だけでは 0%。足したい語は、そもそもリストに無い語だから。
- 字幕の語から取ると、1か所の綴りミスは **上位3件に 100%（1位に 99%）**、2か所のミスでも **81%** が入る（6作品・211語）。
- 出し方は、候補を **最大3語・各1文（📍時刻と出典つき）**、それに「どれでもない（入力のまま例文なしで追加）」。
- 字幕を探り出す使われ方への対策は、**返した例文の数を今の手動追加の上限（1人×1話で 20文/日・1話全体で 60文/日）に数える**こと。こうすれば、1日に引き出せる文の上限は今と変わらない。
- 工数は 約2.5日（サーバ 1.3日・画面 1日・リスト内の綴りチェック 0.25日）。

## 1. 今の流れ（2026-10-30 時点のコード）

- 画面 `components/VocabScreen.js` `handleAddWord` → `POST /api/example`（`mode:'manual'`）。
- サーバ `app/api/example/route.js`:
  - 層1: vocab_cache の字幕語（drama）と語形込みで一致すれば、その例文。
  - 層2: ログイン必須。`manualWordProblem`（3字未満・複数語・頻出語は不可）を通った語だけ、raw キャッシュ（無ければ取り直し枠の範囲で1回取得）から**完全一致（活用形込み）の1文**を返す。上限は `EXAMPLE_MANUAL_LIMITS`（1人×1話 20/日・1話全体 60/日・1分 10）。
- 見つからなければ `no_match` になり、**入力どおりの綴りで例文なしのまま保存**される（受付の確認どおり）。

## 2. 実測（本番データを読み取りのみ・作業用フォルダで）

- 対象: raw キャッシュがある6本。Suits S1E6、Friends S1E1（リスト無し）、Breaking Bad S1E1、プラダを着た悪魔、Loki S1E1、ファルコン＆ウィンター・ソルジャー S1E1。
- 「足したい語」は、字幕にあってリストに無い語。4字以上で、頻出語・固有名詞（8割以上が大文字始まり）は除く。1話あたり 125〜365語で、そこから1話40語まで無作為に選んだ。
- 綴りミスは6種類を機械的に作った: 1字抜け／重ね字の過不足／隣の字の入れ替え／母音の取り違え／キーボードの隣のキー／音の綴り違い（ph→f・-tion→-sion・-ence↔-ance・ie↔ei など）。ミスの結果がたまたま字幕にある別の語になった場合は除外した。
- スクリプト: `reports/add-word-spell-mock/measure/measure.mjs`（git 管理外）。

| 候補の取り元 | 1か所ミス 上位1件 | 1か所ミス 上位3件 | 2か所ミス 上位3件 |
|---|---|---|---|
| 単語リストの語（vocab_cache） | 0% | 0% | 0% |
| その話の字幕の語（raw） | 99% | 100% | 81% |

- 種類別（1か所ミス・上位3件）: 1字抜け 98%、ほかの5種類は 100%。
- 2か所ミスで外れるのは短い語（`clnb`→climb、`wekc`→wreck など）。許す範囲を広げると無関係な候補が増えるので、ここは追わない。
- 例: suspiciun→suspicion・suspicious／handkuffs→handcuffs／gntlemen→gentlemen／reileved→relieved／tradrr→trader・trades・grader。
- **正しく綴った実在の語で、その話に無いもの**を入れた場合も、14〜15%で候補が出る（平均 1.3語。例: soap→soup）。「どれでもない」で抜けられる。これが探り出しに使える入口の大きさでもある（§5）。
- 限界: ミスは機械的に作ったもので、実際の利用者のログではない。affect/effect のような「別の実在語との取り違え」は、入力した語が字幕にあればそのまま当たるので、この機能の対象外。

## 3. 候補の取り方と出し方

1. 先に**画面の中で**、この話のリストにある語との近さを見る（サーバに聞かない・法務上の追加なし）。リストの語の綴り違いなら「リストにある jeopardy ですか？」と出し、その語の行へ飛ぶ。今の「すでにリストにあります」は完全一致しか見ていない。
2. リストに近い語が無ければ、今までどおり `/api/example` に聞く。完全一致（活用形込み）が無い時だけ、同じ要求の中でサーバが字幕の語から候補を作る。**要求を1回増やさない。**
3. 応答は `{ found:false, reason:'no_match', suggestions:[{ word, sentence, tsSec, tsLabel }] }`。候補は最大3語で、各1文を `trimExampleToSentence`（200字）に通す。
4. 画面（モック: `reports/add-word-spell-mock/スマホ-候補シート（モック）.jpg`）:
   - 入力欄の下にシートを出す。「『suspiciun』はこの話の字幕に見つかりませんでした。この語ですか？」
   - 各候補は 語・📍時刻・例文（語を強調）・出典（📺 作品 SxE（字幕：OpenSubtitles）＝48条）と「この語で追加」ボタン。
   - 最後に「どれでもない（入力のまま例文なしで追加）」。
   - 選んだら、今の「追加直後のカード（意味・例文・発音）」へそのまま進む。
5. 候補が0件なら、今までと同じ（例文なしで追加し、理由を一言添える）。

## 4. 近さの判定（工数つき）

| 項目 | 中身 | 工数 |
|---|---|---|
| 編集距離 | OSA（隣の字の入れ替えを1と数える）。許す距離は 5字以下=1・6〜9字=2・10字以上=3。入力が4字未満なら候補を出さない | 0.3日 |
| 音の綴り違い | ph→f・c/k・重ね字・母音をそろえた形が一致すれば距離1とみなす | 0.2日 |
| 語形変化 | 同じ語の活用形（suspicion/suspicions など）は `wordStems` で1つにまとめる。表示するのは字幕に実際に出た形。「原形を入れたが字幕は -ing 形」は今の一致処理（活用形込み）で既に当たるので、綴りミスの扱いは要らない | 0.2日 |
| 大文字小文字・記号 | 入力も字幕も小文字にそろえ、アポストロフィを統一。固有名詞（8割以上が大文字始まり）と頻出語（`COMMON_WORDS`）は候補にしない | 0.1日 |
| 並べ順 | 距離 → 先頭の字が同じ（綴りミスで頭文字が変わることは少ない）→ その話での出現回数 | 含む |
| テスト | 実データの綴りミス表（上の6本）で回帰テスト | 0.3日 |
| サーバへの組み込み | `no_match` の分岐に候補作りを足す・例文数で上限を数える | 0.5日 |
| 画面 | 候補シート・選んだ後の追加・リスト内の綴りチェック | 1日 |

合計は約2.5日。計算は1話の字幕（30〜150KB・異なる語 150〜450）に対して数ミリ秒で、Claude や外部 API の費用は増えない。

## 5. 字幕を探り出す使われ方への対策

- **例文の数で数える**: 候補につけて返した例文1文ごとに、今の手動追加の上限（1人×1話 20/日・1話全体 60/日）を1つ使う。1回の入力で最大3文が出るので、上限に達するまでの入力の回数は減るが、1日に引き出せる文の総数は今と同じ。
- **入力に近い語しか返さない**: 距離の許容範囲の外の語は返さない。任意の語を入れて字幕の語の一覧を引き出すことはできない（正しく綴った実在の語で候補が出るのは 14〜15%・平均 1.3語）。
- **条件は今の層2と同じ**: ログイン必須・頻出語や3字未満は不可（加えて候補は4字以上の入力だけ）。
- **返すのは語と1文だけ**: 前後の文や、話の中の位置の並び（全出現の時刻）は返さない。時刻は候補ごとに1つだけ。
- 候補は保存も共有キャッシュへの書き込みもしない。ログには件数だけを残す（語や本文は残さない）。
- 代わりの案: 候補の語だけ先に返し、例文はタップした時に取りに行く。外に出る文はさらに減るが、通信が1回増え、オーナーの「例文つきで確認」から少し外れる。法務がより狭くと言えばこちら。

## 6. 法務に確認が要る点（受付経由で回答待ち）

1. raw キャッシュ由来の**候補の語**（利用者が入力していない語）を返してよいか。今の層2が返すのは、入力した語の完全一致の1文だけ。
2. 候補ごとに1文（最大3文）を返し、上限を「文の数」で数える方式で足りるか。それとも §5 の代わりの案（例文はタップ後）にするか。
3. 画面の中のリスト内チェック（§3-1）は vocab_cache の語だけで完結するので、追加の確認は要らない想定。
