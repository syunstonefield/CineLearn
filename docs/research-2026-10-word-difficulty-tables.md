## 2. 入れ方

1. **置き場所 = サーバ側 lib に同梱（DB 表は不要）**。約9,900行の `{word: {level, pos}}` JSON で約150KB・gzip 50KB 程度。更新頻度ゼロなので DB に持つ理由がない。クライアントへは今まで通り語ごとの `level` 値だけが届く（既存フィールド・互換性問題なし）。wordfreq を足す場合も英語 Zipf≥3 で 300〜500KB、サーバ同梱のみ（クライアントに配らない）。
2. **lemma（原形）のひも付け**: CEFR-J／Octanove は見出し語＝原形＋品詞。語リストの `word` は原形が大半だが活用形も混ざるので、生成パイプライン（`/api/vocab-generate`）に軽量 lemmatizer を1段挟む（規則ベース -s/-es/-ies/-ed/-ing/-er/-est ＋ 不規則表、または npm の小さな lemmatizer）。品詞で段階が違う語（run 動詞 A1／名詞 B1 等）は**易しい方**を採る（学習者に厳しくしない方向）。本格的な lemma 基盤（growth-features-strategy の本命3機能の1つ）とは別に、ここでは lookup 用の最小実装で足りる。
3. **表に無い語**: 句動詞・イディオム・固有表現・ドラマ口語（gonna, buddy, freak out…）は CEFR-J にほぼ無い。→ **現状どおり AI の level をフォールバック**。wordfreq を入れる場合は Zipf→CEFR の粗い換算（例: ≥5.0→A2以下・4.0〜5.0→B1・3.5〜4.0→B2・3.0〜3.5→C1・<3.0→C2。要校正）を「AI 判定より低優先の参考値」として持つ。
4. **保存**: `vocab_cache` の `level` を表由来で上書き（新規生成分）。出所を区別する列 `level_src`（'table' | 'ai' | 'freq'）を足すと後で検証・巻き戻しができる。既存キャッシュは**一括埋め戻しスクリプト**（語→表 lookup のみ・AI 不要・無償）。

## 3. 使い道

### ① レベル判定（firstQuality × 段階）
- SRS エントリは `level` を持たない（lib/storage.js `reviewWord` 実測）。今は語の段階を知るには作品ごとの語リストを引くしかなく、同じ語が作品で B2/C1 とぶれる＝境目が霞む。**固定表なら語→段階が一意**になり、段階ごとの「知ってた率」が安定する。
- 集計: `firstLearnStats` を段階別に拡張（recorded/known を A1〜C2 で分ける）。「知ってた率が50%を切る最初の段階」＝境目 → 設定画面の**レベル提案**（点数は見せない・罪悪感 UI 禁止の憲法どおり）。
- firstQuality は 2026-10-29 以降の新規語にしか付かないので、提案を出すには最低語数のしきい値（例: 段階あたり10語以上）が必要。データが溜まるまで数週間。

### ② personalizeWords の帯フィルタの置き換え
- 今: `w.level`（AI 判定）で帯の内外を判定。複数語・context tier は免除。
- 案: `level_src==='table'` の語は表の段階、無い語は AI 判定（現状）。免除ロジックは維持。
- **既存キャッシュへの影響**: 埋め戻しで level が変わる語が出る → ユーザーに見える語リストの中身（出る／出ない）が変わる。特に B2↔C1 の境目の語。埋め戻し前後の件数差を数作品で実測してから本番反映。CEFR-J は教育語彙寄りで「ドラマ語」を低く見積もる懸念は無い（無い語は AI に戻るだけ）。

## 7. 単語リストの絞り込みへの反映の検討（2026-10-30・報告書の選択肢2・検討と実測のみ）

### 7.1 いまの流れ
- 生成済みの語リスト（vocab_cache）は、サーバの `wordsForServe`（lib/server/vocabCache.js）を通って `/api/vocab` と `/api/vocab-generate`（命中・生成直後）の3経路でクライアントへ返る。出口はここ1か所。
- 学習者レベルでの絞り込み `personalizeWords` は**クライアント**（components/VocabScreen.js）で、語ごとの `level`（AI 判定）を使って動く。絞った結果が履歴に保存される。
- 語の `level` はどの画面にも描画されていない（履歴とクラウド同期に保存されるだけ）。
- 表は server-only（法務 条件4）なので、クライアント側で表を引くことはできない。

共通の前提: 品詞を合わせて引くため、JSON に品詞ごとの段階を残す形へ変換を変える（現 JSON は品詞を捨てて易しい方だけ）。レベル判定（SRS は品詞を持たない）は今まで通り易しい方を使う。この変更は 0.5 日（上の工数に含む）。

### 7.6 実装（2026-10-30・オーナー決定＝(a2) サーバで絞り込み）
- 表のファイルを品詞ごとの段階を持つ形に作り直した（`"go": {"noun":"B1","verb":"A1"}`）。見出し語数・段階別の件数は変わらない（レベル判定の結果も変わらない）。Octanove の品詞の誤記 vern は verb に、空欄は unknown に正規化（`_modified` に明記）。
- `lib/wordLevelLookup.js`: `lookup(word, { pos, exactOnly })` と、絞り込み用の `makeFilterLevelOf`（単語・context 以外・品詞一致・原形化なし）。
- `lib/personalize.js`: personalizeWords を lib/vocab.js から分離（クライアント依存なし）。`levelOf` を受け取り、その段階を優先・無ければ AI の level。`selectIndices`・`parsePersonalize`。
- `/api/vocab-generate`: body に `personalize`（TOEIC・目標・語数）があれば、全語（AI の level のまま）に加えて**表示する語の添字 `selected`** を返す。表の値はサーバの外に出ない。全語を返し続けるのは、例文和訳の行ごと埋め戻し（runFillExampleJa）が行の全語を使うため。
- 画面（VocabScreen）: `personalize` を送り、`selected` があればその語だけを表示。無ければ従来どおり自分で絞る（古い画面のコード・seed・`WORD_LEVEL_FILTER=off` の時）。
- 戻し方: Vercel の環境変数 `WORD_LEVEL_FILTER=off` を入れて再デプロイ。DB は触っていないので後始末なし。
- 確認: ローカルの本番ビルドで本物の共有キャッシュに対し 5 作品 × TOEIC 3 段を叩き、表示語数が 7.2 の実測（原形化なし）と 15 通りすべて一致、返る語の level は全件 AI のまま、設定を送らない呼び出しには selected が付かないことを確認。テスト 175 件パス。

## 8. 頻度データ（wordfreq の Zipf）で TOEIC 100点刻みに近い難易度を出せるか（2026-10-30・調査のみ）

実測: 本番 vocab_cache 65話・6,571語（読み取り専用）、wordfreq 3.1.1（英語・データは 2021 年で凍結）。作業は一時フォルダのみ・コード変更なし。

### 8.1 引ける割合と一致度
- 単語（空白なし）6,072語のうち **99.8% に Zipf 値がある**（引けないのは Sokovian・synthezoid のような作中造語だけ）。異なり 3,828語のうち CEFR-J/Octanove に載るのは 51% なので、**表に無い 1,855語も頻度なら引ける**。
- 句動詞・イディオム（複数語）499語は、wordfreq が語の組み合わせから推定した値しか出ず、句としての頻度ではない → 使えない（今まで通り AI）。ハイフン語（cut-up・mind-control）も部品の頻度で高く出る。
- 順位相関（異なり単語）: Zipf×表 **ρ=0.67**、Zipf×AI ρ=0.61、表×AI ρ=0.64。どれも「同じ向きだが、語ごとにはかなりずれる」水準。
- 表全体で段階ごとの Zipf 中央値は A1 4.97・A2 4.49・B1 4.12・B2 3.67・C1 3.25・C2 2.84 ときれいに下がるが、各段階の中のばらつき（SD 約0.64）が段階の間隔（約0.4）より大きい。**隣り合う段階を頻度だけで見分けられるのは 63〜65%**（偶然で50%）。
- 頻度と難しさがずれる典型: black（黒字の）・cross（反対尋問）・charge・bank・plant のような**多義語の別の意味**。頻度は綴りの頻度なので、ドラマで教えたい難しい意味を易しい語と判定してしまう。

### 8.2 TOEIC への換算と刻みの限界
- 換算は「CEFR-J の段階ごとの Zipf 中央値」と「ETS の CEFR 下限（A1 120・A2 225・B1 550・B2 785・C1 945）」を区間ごとに線形でつなぐのが素直。TOEIC 100点あたりの Zipf は A2→B1 区間で 0.11、B1→B2 で 0.19、B2→C1 で 0.26。
- **語1つの難易度を TOEIC 点数で言う精度は ±140〜570点**（区間による）。語ごとの 100点刻みはもちろん、200点刻みも無理。
- **学習者の境目**は多くの語の答えから推定するので細かくできる（シミュレーション・語の誤差は上の値、境目付近の答えのゆらぎ幅50点と仮定）:

| 初回の答えの語数 | 誤差の中央値 | 90%が収まる幅 |
|---|---|---|
| 30語 | 112点 | 249点 |
| 60語 | 85点 | 197点 |
| 120語 | 65点 | 155点 |
| 240語 | 51点 | 133点 |
| 480語 | 41点 | 102点 |

- 結論: **100点刻みは初回の答えが 250〜500語たまってから、それまでは 200点刻みが限度**。換算の基準（ETS の CEFR 対応）自体の粗さはこの誤差に含めていないので、実際はもう少し粗い。

- 同梱するのは英語の単語（英字・アポストロフィ・ハイフンのみ）と Zipf 値（小数1桁）の JSON。サーバ専用（server-only・CEFR-J と同じ条件）。

### 8.4 使い道
1. **レベル判定**（firstQuality × 頻度で境目を連続値で推定）: 効果あり。表に載る語の 2倍の語が使えるので、境目が早く定まる。工数 1.5日（変換 0.5・lookup とテスト 0.5・推定の連続値化 0.5）。ただしレベル判定自体が 11月末まで保留中で、初回の答えは語ごとに保存されているので**後から頻度を当てても同じ結果になる**＝今入れる理由は無い。
2. **単語リストの絞り込み**: 非推奨。表に無い語を AI の段階の代わりに頻度で絞ると、black（黒字の）・cross（反対尋問）のような作品ならではの意味の語が「易しい語」として消える。AI との相関も表と同程度で、置き換えて良くなる根拠が無い。

### 8.5 やめた方がいい点
- 語ごとに「TOEIC ○○点の単語」と出すこと（誤差 ±140点以上）。
- 少ない語数で 100点刻みの判定を出すこと（120語でも誤差の中央値 65点・90%幅 155点）。
- 句動詞・イディオム・ハイフン語に頻度を使うこと。
- 点数をユーザーに見せる形（罪悪感UI禁止）。提案に使うだけにとどめる。
